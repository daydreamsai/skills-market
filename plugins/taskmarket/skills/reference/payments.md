# Payments and X402

This page covers payments to Taskmarket routes. To buy a directly supplied third-party resource
under local origin, recipient, token and rolling-spend policy, load [x402-pay.md](x402-pay.md).
`taskmarket x402 request` pays a seller that charges through x402, or through MPP on Tempo (the
`tempo` method, `charge` intent). That is separate from the Tempo MPP flow below, which is how
Taskmarket's own API is paid and is unchanged.

Each chain has one payment token with six decimals: USDC on Base and Base Sepolia, OUSD on Tempo. REST amounts are integer base-unit strings. CLI monetary flags are human-readable whole tokens. The prices below are in the payment token: 0.001 is 0.001 of the payment token on Base and 0.001 OUSD on Tempo. A total that combines chains is a sum of base units read as dollars, not an amount of one token.

```text
1 token     = 1000000 base units
0.001 token = 1000 base units
```

## Paid Routes

Task creation costs the reward, which is held until you choose who to pay. Every other route in this table costs 0.001 of the payment token, except that a task reward increase also collects the exact amount added to the reward.

Send an `X-Taskmarket-Idempotency-Key` UUID on both rounds of every paid route. On a paid route it is optional: a paid request without it is still served. It is recommended because the key is what ties the payment intent to one logical write across retries. Without it the backend can identify the intent only by the signed payment authorization, and a retry signs a fresh authorization, so the retry is recorded and charged as a second operation (on `POST /api/tasks`, a second held reward), and you hold no key to look the first write up with in `GET /api/intents`. A key that is present but not a UUID is refused with `idempotency_key_required`. A free relayed write (see Free Writes) requires the key and is refused with the same reason without it. The `taskmarket` CLI always sends one. See [raw-api.md](raw-api.md#idempotency-key).

The `accept` body is `taskId`, `worker` and an optional `submissionId`, the submission being accepted. It must be on the task, by that worker and not rejected, or the API answers `400` before any payment is taken; on a task that is not a bounty or benchmark it must also be the worker's latest. Without it the worker's latest active submission is accepted. The accepted submission is recorded as the award's `submissionId`.

Only the task's requester may call `accept` and `accept-submissions`: the X402 payer must be the requester address, or the backend answers `403`, and the contract checks the relayed sender the same way. An evaluator never calls `accept`. On a task with an evaluator, `accept` is refused before any payment is taken: the API answers `400` with reason `payment_preflight_rejected` and the message `Task uses an evaluator; use evaluate instead`, and the contract itself reverts `UseEvaluate`. The outcome comes from `evaluate`, `finalize-verdict` or `evaluator-timeout`. When a Claim, Pitch or Auction delivery's review window lapses undecided, anyone may settle it to the worker with `settle`, exactly as an accept would.

## Free Writes

These operations do not require X402:

- claim a claim-mode task (the claim itself carries no X402 charge, but a task that requires a stake charges the stake with the claim: see [settlement-terms.md](settlement-terms.md));
- upload and submit artifacts;
- select the deterministic lowest auction bidder after the deadline;
- forfeit an expired claim with the requester's EIP-191 signature;
- finalize a verdict after the appeal deadline;
- publish a key with device credentials.

Free does not mean permissionless. The router and contract still enforce the wallet, signature, role, state, and deadline.

## Approval

Before a paid request, state:

- task ID and mode;
- network (Base, Base Sepolia, Tempo or Tempo Moderato: `--network base|base-sepolia|tempo|tempo-testnet`);
- acting wallet;
- requested operation;
- X402 charge;
- held reward, bid, award, refund, or payout amount affected;
- selected worker or submission when relevant.

Obtain explicit user approval for that exact action.

## Two-Round Flow

Before either round, the request can return `403 LEGAL_ACCEPTANCE_REQUIRED` instead of proceeding to payment; see [failure-modes.md](failure-modes.md).

The first request receives HTTP 402 and payment requirements. The CLI signs an EIP-712 `TransferWithAuthorization` and retries with `PAYMENT-SIGNATURE`. Before settlement, the backend re-checks current task state and the declared payer for paid task actions. The router and contract repeat authorization and invariant checks after settlement.

Re-fetch and validate `pendingActions` immediately before signing. Preflight cannot eliminate a race with another transaction after the check. Do not blindly retry a paid request: a payment or onchain transaction may have succeeded even if the final API response was lost.

For reward updates, compare the returned payment requirement with the current task. Raising reward from `5000000` to `7000000` base units requires `2001000`: the `2000000` added to the held reward plus the `1000` action fee. Decreases and non-reward updates require only `1000`.

## In-Flight Paid Writes: Why

The actionable rules are in the In-Flight Paid Writes section of `../skill.md`; this is the background behind them.

A paid write is **two separate onchain transactions**, and keeping them apart is what makes the rest of this section make sense. The **x402 payment** is settled by the facilitator before the request ever reaches the handler -- by the time a write is attempted at all, that money has moved. The **relayed write** is a second transaction the backend broadcasts through its own wallet, and the chain can take longer to confirm it than the command waits. When that happens the relayed write has been broadcast and is still live, and the backend finishes the work from its own durable record once the chain confirms it. This **in flight** state is a third outcome alongside success and failure.

It is reported as its own result. An in-flight write answers HTTP **409** with `reason: "intent_in_flight"` in the error envelope, carrying the intent id, the intent's status and the relayed write's transaction hash. **Branch on `reason`, never on the message text** -- the message is free to change and matching it is how a client silently starts reading a settled failure as "still confirming". The CLI does this for you on every command, paid or not: its failure envelope carries `pending`, `reason` and `intentId`, and `pending: true` means the write may still succeed. A failure that carries no `pending` at all means the backend sent no envelope -- treat that as unknown, never as safe. A repeated idempotency key answers 409 with `reason: "idempotency_key_reused"` and an `intentStatus`; that is in flight while the status is `reserved`, `recorded` or `broadcast`. `reserved` means another request holds that key and is partway through paying for it -- nothing of yours was charged, and starting again with a fresh key would be a second payment for the same operation.

A private-auction bid or auction accept is checked again just before it is sent. If the requester removed you from the task's allowlist after your request was recorded, nothing is sent and your payment is refunded: the request answers HTTP **403** with `reason: "payment_landed_action_refused"`, `intentStatus: "failed"` and the `intentId`, and the message says the payment was refunded. Do not pay again; read the intent by that id to see its refund.

An in-flight result still tells you nothing about whether the payment will be kept or refunded -- a request that got that far has paid, and only settlement decides. And when the envelope is absent (no response at all, a dropped connection, an older deployment), you are back to the old rule: treat the outcome as unknown and possibly in flight. What cannot be taken away from you is the idempotency key, chosen before sending and reported back to you, which is the handle to ask with.

A retry after `intent_in_flight` with the same idempotency key, route, body and payment credential is checked after the backend has looked for your landed payment, not before. The pre-payment checks that refuse a fresh request (a task's identity or verifier requirement, a claim you are no longer eligible for, the per-worker submission ceiling, a voided compute credit purchase) run again at that point. If the payment landed and one of them now refuses the action, the answer is HTTP **409** `payment_landed_action_refused` naming the intent, and a definite refusal refunds the payment (the message gives the refund transaction); do not pay again. The submission ceiling is the exception: it is counted when the submission is admitted, and answers `429` with a message naming the intent and saying the landed fee is refunded. A refusal that may be transient (a verifier that could not answer) refunds nothing; the payment stays with the reservation for a later retry, or is held for review and refund once it expires. A fresh request, including one that carries a payment header, still meets those checks before anything is charged.

An unconfirmed result is never evidence that the relayed write failed. Only a reverted receipt for that transaction, or a replacement confirmed at the same nonce, can mark it failed -- a merely slow transaction can still land minutes later. Treating a timeout as failure and paying again is the single most expensive mistake available on this platform, precisely because the payment half has already settled: a repeat is a second settled payment, not a retry of the first. Failures reported before the relayed write is broadcast -- validation errors, and contract calls that revert deterministically in simulation -- are genuinely failed and are not this state.

## Retrying a Paid Write Under Its Key

The backend binds each paid write to its request body. A reservation records a hash of the canonical body (key order and absent fields do not matter, every value does), a same-key retry adopts that reservation only when its body hashes the same, and an MPP challenge is bound to the route and the body hash. Change any body field between the `402` round and the paid round, or between same-key retries, and you get a fresh `402` or no adoption.

So a retry under `TASKMARKET_IDEMPOTENCY_KEY=<key>` must send the body it sent the first time. The CLI does this for you: it keeps the exact body of each catalog or hook listing submission, the paid writes it re-signs on every run, under `~/.taskmarket/paid-writes/` (owner-only, and never a body carrying a token or key) until the write succeeds (records are pruned after seven days), and a re-run under the same key sends those bytes again, though the command signed a fresh wallet-write proof (`nonce`, `expiresAt`, `signature`) for it. A stored proof within 30 seconds of its expiry is not resent; the command's fresh one is, unless `intents.get` shows the key already completed its write. Then the stored body is sent as it is, and the backend refuses it at the reservation, before any payment settles or the proof is checked, so the CLI can read back the completed write. A re-run whose other fields differ is a different write and is sent as given, and the backend does not adopt the earlier payment for it. A lost compute-credit purchase is asked for again with the body it was paid with, even if the selected network or device token changed since.

A key that already completed a paid write that changes the database directly (project workflows, schedules, suggestions and templates, project review settings, task metadata updates and catalog or hook listing submissions) is challenged as usual. The paid round is then refused with `409 idempotency_key_reused`, `intentStatus: "completed"`, before anything settles, so nothing is charged. The envelope carries `sameRequest`, only when the presented payment is from the wallet that paid for the intent: `true` when this request has the same route and body hash the intent was paid for, `false` when the key is being reused for something else. `GET /api/intents?idempotencyKey=<key>` returns the write's stored result in a `result` field, but only to its payer signing read-auth. Anyone else, including a caller presenting only the key, gets the status without `result`. The stored result is a summary holding the ids the write produced, such as `{ "workflowId": "..." }` or `{ "scheduleId": "...", "status": "active" }`, not the full response the first run returned. When `sameRequest` is `true`, the CLI reads the intent and prints that summary as the command's `data`, with `replayed: true` and the `intentId`. Otherwise it reports the refusal.

## Tempo (MPP)

On Base, paid routes speak x402. On a Tempo chain the same routes speak MPP, and the paid request names the chain in its body (`chainId`). Side by side:

| Step                 | Base (x402)                                            | Tempo (MPP)                                                                                                                                  |
| -------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Challenge            | `402` with `PAYMENT-REQUIRED`                          | `402` with `WWW-Authenticate: Payment` (method `tempo`, intent `charge`)                                                                     |
| What the payer signs | EIP-712 `TransferWithAuthorization` (EIP-3009) on USDC | A Tempo transaction calling `transferWithMemo` on OUSD to the server wallet, memo bound to the challenge, fee-payer slot left for the server |
| Retry header         | `PAYMENT-SIGNATURE`                                    | `Authorization: Payment <credential>`                                                                                                        |
| Receipt header       | `PAYMENT-RESPONSE`                                     | `Payment-Receipt`; on `POST /api/tasks` its `externalId` is the created task's id                                                            |
| Gas                  | paid by the platform                                   | paid by the server as fee payer                                                                                                              |

No setup step, allowance or approval is needed on Tempo. The signed transfer uses an expiring nonce valid for about two minutes, so concurrent paid writes from one wallet do not interfere. The CLI retries a request that failed in transit, or got `502`, `503` or `504`, with the same signed transfer, never a new one. A `409` with reason `intent_in_flight` means the transfer was submitted and its outcome is not known yet: do not pay again; re-run with `TASKMARKET_IDEMPOTENCY_KEY=<key>`. A `409` with reason `recipient_receive_policy_blocked` means a payout recipient's TIP-403 receive policy would block the payout; nothing was paid. See [tempo.md](tempo.md).

**Signing keys.** An MPP payment may be signed by the paying account's own secp256k1 key or by a Tempo access key (a keychain signature) that the account's root key authorized on chain. An access-key payment is attributed to the root account the key acts for, never to the access key's own address, so the task, refunds and receipt belong to that account; a credential `source` must name the root account. Before co-signing, the server checks that the key is registered for that account and is not revoked, that it does not expire before the transaction's `validBefore`, that its call scopes (if any) allow a `transfer` or `transferWithMemo` of the payment token to the server wallet, and that its remaining spending limit for the payment token covers the amount; it refuses the payment with `402` and a message naming the failed check otherwise. To recover, raise the key's limit, sign with a shorter validity window or a longer-lived key, widen its scopes, or pay with another key. A gas-sponsored Tempo withdrawal (`wallet withdraw`, `method: "signed-transfer"`) may also be signed by an access key of the withdrawing wallet, under the same rules: it is attributed to the root account, which must be the request's `from`, and still pays only the withdrawal address registered on that chain the requested amount. The server runs the same key checks before co-signing and refuses the withdrawal with `400` and a message naming the failed check. The `taskmarket` CLI signs withdrawals with the wallet's own key; an access-key withdrawal comes from a client that holds the access key.

**Signed messages.** On a Tempo chain, every wallet signature over a Taskmarket message (claim, submit, release, forfeit, review, set-withdrawal-address and the rest, plus the `X-Taskmarket-Caller-Signature` read-auth header) may also be a Tempo access-key signature (the withdrawal address and recovery code are per chain, so an access key sets or reveals only that Tempo chain's): the 86-byte V2 keychain envelope `0x04 || account || r || s || v`, where the access key signs `keccak256(0x04 || hashMessage(message) || account)`. `account` must be the address the request names, and the action is that account's. The key must be registered for the account, not revoked and not expired at the latest block; otherwise the signature is refused as for a wrong signer. The older V1 envelope (`0x03`) is refused, and so is an access-key signature on a non-Tempo chain. Withdrawal transactions stay root-key only.

In v1, paid writes on Tempo come from the CLI or a third-party MPP client only.

## Amounts and Auctions

CLI reward, price, award, and `--min-price` flags use human-readable amounts of the selected network's payment token (USDC on Base, OUSD on Tempo). REST monetary fields use integer base units with six decimals. An amount that belongs to one chain names that chain's token. `totalEarnings` is per chain: it is what the wallet was paid on the requested chain, in that chain's token; `earningsByChain` lists every chain separately and is never summed.

For auctions, `--max-price` must equal `--reward` because the reward is the held maximum. A Dutch auction also requires `--auction-floor-price`; a reverse Dutch auction requires `--auction-start-price`.

`netReward` is the aggregate worker payout pool after platform fee. It is null for an open auction whose winning price is not known. After selection it is based on the winning price, not the held maximum. For a split acceptance it is the aggregate pool, not one worker's share. The platform fee is 0% on every chain for new tasks; a Base task created before the fee was set to 0 keeps 7.5%, so read its `platformFeeBps` or `netReward`.

## Auction Held Reward

For auction creation, REST `maxPrice` must equal `reward`; the reward is the maximum actually held onchain. The CLI enforces the same equality before payment.

An auction worker payout is based on the winning bid or accepted clock price, less the platform fee. The unused part of the held reward is returned according to the contract flow.
